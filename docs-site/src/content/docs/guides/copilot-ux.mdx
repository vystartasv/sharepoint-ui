SPFx 1.24 made Copilot UX components generally available: a declarative agent can invoke an interactive component directly in the Microsoft 365 Copilot conversation. A conventional SPFx web part renders on a SharePoint page; it cannot appear as an invoked component in the Copilot canvas. This is where SharePoint UI has a useful edge: compose the tenant-themed task view from the same library patterns, then describe the visible state back to Copilot.

## Explore the access-review flow

This preview uses SharePoint UI's real web components. Search, theme, direction, display-mode, and review actions work locally. Its sample records are illustrative; the preview does not connect to a tenant or save approvals.

For the tenant-connected implementation, start with the [buildable SPFx 1.24.1 Copilot example on GitHub](https://github.com/vystartasv/sharepoint-ui/tree/main/examples/spfx124-copilot-ux). It reads and updates a real SharePoint list with the signed-in user's permissions, applies SharePoint `ThemeProvider` tokens, and updates Copilot's model context as the visible view changes. The README has the run and deployment steps.

To generate this pattern directly with the [SPFx CLI custom template](https://github.com/vystartasv/sharepoint-ui/tree/main/templates/spfx-fast-copilot-access-review), run this from a repository checkout:

```sh
npx --yes @microsoft/spfx-cli@0.1.0-pre.3 create \
  --template spfx-fast-copilot-access-review \
  --library-name spfx-fast-access-review \
  --component-name "Access review" \
  --component-description "Review SharePoint access items in Copilot" \
  --solution-name spfx-fast-access-review \
  --package-manager npm \
  --local-source ./templates
```

At GA they work in browser and desktop clients; iOS and Android clients are not supported. Start new projects on SPFx 1.24.1. This docs preview is available without a Copilot license.

## Why it matters

The agent can turn an intent such as “show open reviews that need attention” into a SharePoint-themed task surface. A user can inspect the owners, scope, and state, then take an action inside Copilot without leaving the conversation. Use `ViewCard`, `Badge`, `Tag`, `Avatar`, and `Button` to build that surface; keep list access, permission checks, and writes in the SPFx component's data service.

SPFx declares the tool and its parameters in the Copilot component manifest. A Zod schema describes the arguments for the agent:

```ts
import { z } from "zod";

export const propertiesSchema = z.object({
  listId: z.string().uuid().describe("The SharePoint list ID containing access reviews."),
  query: z.string().max(120).optional().describe("Optional title or status to find in the list."),
});
```

The example expects the list's default `Title` field and a single-line text `Status` field. It reads the 25 most recently modified items and writes `Status: "Approved"` only after the user selects **Approve**. SharePoint permissions enforce read and edit access.

The component manifest exposes a tool and supported Copilot display modes. This is the relevant shape; keep the identity and version fields generated by SPFx:

```json
{
  "componentType": "CopilotComponent",
  "copilotType": "Ux",
  "capabilities": {
    "availableDisplayModes": ["inline", "fullscreen"]
  },
  "tools": [{
    "name": "showAccessReviews",
    "description": { "default": "Find and display the user's authorized SharePoint access reviews." },
    "propertiesSchema": {
      "id": "$../../../lib/copilotComponents/accessReview/AccessReviewProperties.js:propertiesSchema;"
    }
  }]
}
```

The generated component extends `BaseCopilotComponent`. Its `render()` mounts the view inside `this.context.domElement`; SPFx supplies tool properties and display mode. React is optional. In a no-framework component, import only the custom elements used and build them with DOM APIs:

```ts
import { defineButton } from "@spfx-fast/sharepoint-ui/elements/button";
import { defineTag } from "@spfx-fast/sharepoint-ui/elements/tags";
import { defineViewCard } from "@spfx-fast/sharepoint-ui/elements/view-card";

defineButton();
defineTag();
defineViewCard();

type Review = { id: string; title: string; owner: string; status: string; needsAttention: boolean };

function renderReview(target: HTMLElement, review: Review, onApprove: () => void) {
  const card = document.createElement("spui-view-card");
  card.setAttribute("kind", "approval");
  card.setAttribute("title", review.title);
  card.setAttribute("subtitle", review.owner);

  const status = document.createElement("spui-tag");
  status.slot = "status";
  status.setAttribute("color", review.needsAttention ? "warning" : "informative");
  status.textContent = review.status;

  const approve = document.createElement("spui-button");
  approve.slot = "actions";
  approve.setAttribute("appearance", "primary");
  approve.textContent = "Approve";
  approve.addEventListener("click", onApprove, { once: true });

  card.append(status, approve);
  target.replaceChildren(card);
}
```

Or use the React adapter with the same controls and view pattern as a web part:

```tsx
import * as React from "react";
import { SharePointUIProvider, ViewCard, Tag, Button } from "@spfx-fast/sharepoint-ui/react";

type Review = { id: string; title: string; owner: string; scope: string; status: string; needsAttention: boolean };
type Props = { locale: string; reviews: Review[]; onApprove: (id: string) => void };

function AccessReview({ review, onApprove }: { review: Review; onApprove: (id: string) => void }) {
  return (
    <ViewCard kind="approval" title={review.title} subtitle={review.owner} description={review.scope}>
      <Tag slot="status" color={review.needsAttention ? "warning" : "informative"} size="small">
        {review.status}
      </Tag>
      <Button slot="actions" appearance="primary" onClick={() => onApprove(review.id)}>
        Approve
      </Button>
    </ViewCard>
  );
}

export function AccessReviewView({ locale, reviews, onApprove }: Props) {
  return (
    <SharePointUIProvider lang={locale}>
      {reviews.map(review => <AccessReview key={review.id} review={review} onApprove={onApprove} />)}
    </SharePointUIProvider>
  );
}
```

SPFx owns Copilot's display-mode transition. The **Expand view** button above simulates that transition inside this docs page; in the actual Copilot component, call the host API:

```ts
await this.requestDisplayModeAsync("fullscreen");
```

## Keep Copilot aware of the visible view

Copilot does not read the component's DOM. After filters or decisions change, send a concise, authorized summary of the current view through the SPFx bridge. The next user message can then refer to the same selected and visible records:

```ts
import { createCopilotTextContent } from "@microsoft/sp-copilot-component";

await this.context.copilotBridge.updateModelContextAsync({
  content: [createCopilotTextContent(
    `Access reviews: ${visibleReviews.length} visible; ${selectedReviews.length} selected; ` +
    `filter: ${query || "all reviews"}. No approval has been submitted yet.`
  )],
});
```

Build that summary from application state, not HTML. Include only data the signed-in user may access, keep it under the 10 KB limit, and don't report an action as complete until the SharePoint service confirms it. The [Copilot component guide](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/copilot/get-started/build-your-first-copilot-app) covers scaffolding, Workbench, packaging, and deployment; Microsoft's [context bridge guide](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/copilot/provide-context-to-copilot) covers state updates and limits.

Start new projects with the [SPFx 1.24.1 generator](https://learn.microsoft.com/en-us/sharepoint/dev/spfx/release-1.24.0). The Copilot surface and host APIs require a licensed Microsoft 365 Copilot user; API calls from your component still need their own data access and authorization. The docs example is an interactive local preview, not proof of a deployed agent.
