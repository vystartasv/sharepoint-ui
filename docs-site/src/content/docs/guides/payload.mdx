---
title: Component payload benchmark
description: Compare the production-style JavaScript payload for SharePoint UI component imports and Fluent UI React v9.
---

SharePoint UI's strongest measured advantage is its framework-free custom-element path. A small no-React view can avoid shipping the React component runtime and a larger styling runtime for the components it uses.

## Measured result

On 2026-11-03, the repository benchmark bundled `Button`, `Input`, `Card`, and `Tag` from SharePoint UI `0.4.2` and Fluent UI React `9.75.0` as minified, tree-shaken browser ESM targeting ES2022. React and React DOM were external in both React builds.

| Import path | Raw JavaScript | Gzip | Brotli | Gzip change vs Fluent |
| --- | ---: | ---: | ---: | ---: |
| SharePoint UI custom elements, no React | 47,858 bytes | 11,560 bytes | 10,256 bytes | 74.0% less |
| SharePoint UI React adapters | 95,567 bytes | 23,590 bytes | 20,737 bytes | 46.9% less |
| Fluent UI React 9.75.0 | 181,420 bytes | 44,411 bytes | 38,069 bytes | Baseline |

This is a concrete advantage for compact SharePoint and Copilot task surfaces: the four-component custom-element slice is 74% smaller after gzip than the matching Fluent imports.

## SharePoint metadata fields

The same benchmark also measures the metadata-driven `SharePointField` renderer and its control registrations. In this import-only slice, the framework-free custom element is 46,356 gzip bytes; the React adapter is 62,177 gzip bytes. The no-React entry is 25.4% smaller. This slice includes the field types and control code the renderer can select; it is not the size of one rendered text field.

| Import path | Raw JavaScript | Gzip | Brotli | Modules included |
| --- | ---: | ---: | ---: | ---: |
| `SharePointField` custom element, no React | 211,010 bytes | 46,356 bytes | 37,955 bytes | 15 |
| `SharePointField` React adapter | 270,408 bytes | 62,177 bytes | 51,250 bytes | 17 |

## Reproduce it

From the repository root, run:

```sh
npm run benchmark:no-react-payload
```

The script builds the library, bundles the package's public element and React entry points, and compares a four-control slice with the Fluent UI version installed by the SPFx demo. It also measures the SharePoint field renderer through both public entry points. The measurements cover JavaScript imports only. They do not measure CSS files, React's host-provided runtime, SharePoint startup cost, render speed, or complete behavioral parity.

Choose custom elements when React is unnecessary or when the same UI needs to work across multiple frameworks. Choose the React adapter when its familiar composition model is useful; it still produced a smaller four-component JavaScript slice in this measurement.
