---
title: Component payload benchmark
description: Compare the production-style JavaScript payload for SharePoint UI component imports and Fluent UI React v9.
---

SharePoint UI's strongest measured advantage is its framework-free custom-element path. A small no-React view can avoid shipping the React component runtime and a larger styling runtime for the components it uses.

## Measured result

On 2026-11-04, the repository benchmark bundled `Button`, `Input`, `Card`, and `Tag` from SharePoint UI `0.4.3` and Fluent UI React `9.75.0` as minified, tree-shaken browser ESM targeting ES2022 with esbuild 0.28.2. React and React DOM were external in both React builds. The source revision was [`ff3f905`](https://github.com/vystartasv/sharepoint-ui/commit/ff3f905f1b615cd70f04ddfe4d4fa50db484ed3b).

| Import path | Raw JavaScript | Gzip | Brotli | Gzip change vs Fluent |
| --- | ---: | ---: | ---: | ---: |
| SharePoint UI custom elements, no React | 47,862 bytes | 11,562 bytes | 10,254 bytes | 74.0% less |
| SharePoint UI React adapters | 95,991 bytes | 23,753 bytes | 20,901 bytes | 46.5% less |
| Fluent UI React 9.75.0 | 181,420 bytes | 44,411 bytes | 38,069 bytes | Baseline |

This is a concrete advantage for compact SharePoint and Copilot task surfaces: the four-component custom-element slice is 74% smaller after gzip than the matching Fluent imports.

## What one component costs

A separate per-component measurement on 2026-11-04 shows how payload follows the import. The editor is deliberately much larger than a basic control because it includes Quill Core and its document, history, table, and format modules. A Button-only import does not include those modules.

| Import | Raw JavaScript | Gzip | Brotli | Included modules |
| --- | ---: | ---: | ---: | ---: |
| Button custom-element leaf | 18,478 bytes | 5,533 bytes | 4,957 bytes | 3 |
| Button React adapter | 61,212 bytes | 16,157 bytes | 14,218 bytes | 5 |
| RichTextEditor custom-element leaf | 242,564 bytes | 69,007 bytes | 59,033 bytes | 202 |
| RichTextEditor React adapter | 288,826 bytes | 81,005 bytes | 69,104 bytes | 206 |

The small import stays small: the measured React Button slice retains the adapter, its shared helper, and Button code; it does not retain RichTextEditor or Quill. Import the editor only where it is used, and use the [lazy-loading pattern](/sharepoint-ui/guides/rich-text-editor/#load-the-editor-only-when-needed) if editing should not load with the initial view. These are independent component slices, not additive totals.

The measurements use the same minify/tree-shake process as the package analyzer. They exclude CSS, React's host-provided runtime, SharePoint startup and rendering work, and do not predict full-page download or interaction time. RichTextEditor is not compared with Fluent's core component set because Fluent UI React does not include a first-party rich-text editor.

These per-component readings describe repository source at [`ff3f905`](https://github.com/vystartasv/sharepoint-ui/commit/ff3f905f1b615cd70f04ddfe4d4fa50db484ed3b), not a measurement of the current npm tarball. RichTextEditor is 3,624 gzip bytes larger than the previous recorded slice; the benchmark does not identify which source changes account for that increase.

## SharePoint metadata fields

The same benchmark measures the metadata-driven `SharePointField` renderer. Eagerly importing every supported control is 116,738 gzip bytes for the custom element and 129,343 bytes for the React adapter: the no-React import is 9.7% smaller. This includes the field types and control code the renderer can select; it is not the size of one rendered text field.

| Import path | Raw JavaScript | Gzip | Brotli | Modules included |
| --- | ---: | ---: | ---: | ---: |
| `SharePointField` custom element, no React | 451,577 bytes | 116,738 bytes | 94,945 bytes | 218 |
| `SharePointField` React adapter | 504,718 bytes | 129,343 bytes | 105,711 bytes | 218 |

The custom-element renderer can split rich text, lookup/person, and date controls into on-demand chunks when the consuming bundler supports dynamic imports. Its entry is 19,949 gzip bytes before a control chunk is requested. The measured entry-plus-required-chunks payload depends on the fields used:

| Fields used | Gzip payload |
| --- | ---: |
| Common text, choice, Boolean, and multi-choice fields | 25,724 bytes |
| Rich-text Note | 91,382 bytes |
| Lookup or User | 34,812 bytes |
| Date or date-time | 32,067 bytes |
| A form using all four groups | 106,813 bytes |

The lazy entry-plus-chunks estimate for a form using all four groups is 8.5% smaller than the eager bundle. A common-fields form is 25,724 gzip bytes. These are build-time estimates; they do not include requests, cache state, or runtime field rendering.

## Reproduce it

From the repository root, run:

```sh
npm run benchmark:no-react-payload
```

The script builds the library, bundles the package's public element and React entry points, and compares a four-control slice with the Fluent UI version installed by the SPFx demo. It also measures the SharePoint field renderer through both public entry points and estimates entry-plus-chunk payloads for common field combinations. The measurements cover JavaScript imports only. They do not measure CSS files, React's host-provided runtime, SharePoint startup cost, render speed, or complete behavioral parity.

Choose custom elements when React is unnecessary or when the same UI needs to work across multiple frameworks. Choose the React adapter when its familiar composition model is useful; it still produced a smaller four-component JavaScript slice in this measurement.
